# Tule Resort app audit — 17 October 2026

## Scope and evidence

This review used the GitHub source on `master` and the latest production deployment metadata/build log available on 17 October 2026. Production commit `36baf9b07c42fd3a15a79411e7b1b0388ebe3774` is marked **READY** on Vercel. The Next.js production build compiled successfully, TypeScript completed, and all 42 static pages generated.

A successful build confirms the application compiles and routes are registered; it does not prove that every role-based workflow or Supabase database function works in production. No authenticated guest/staff/admin browser session or live order transaction was available during this source audit.

## Fixes included in this change

- Guest menu cart now restores valid saved quantities after a refresh; stale and unavailable item IDs are discarded.
- The menu uses a book-style pagination pattern with 10 items per page, Previous/Next controls, and touch swiping. Search and category filters return the guest to page one.
- Total menu/dish counts are intentionally hidden from the guest-facing menu and restaurant landing page; only book page numbers are shown.
- Failed dish photos now fall back to a local, neutral illustration instead of silently showing the same salad photo for unrelated dishes.
- Guest menu filtering excludes rows marked unavailable.
- Checkout now requests the same live menu source as the restaurant page instead of relying solely on the bundled numeric-ID seed data. This addresses the mismatch risk when Supabase returns different menu-item IDs.
- Added a no-cache `GET /api/menu` endpoint to expose the same normalized menu data and preserve the bundled fallback when Supabase is not configured.

## Findings requiring follow-up

### High — verify live order creation against the database function

`POST /api/orders` uses the Supabase service-role key and calls the database RPC `create_guest_order`. The route validates quantities and requires menu-item IDs, but the source alone does not prove that the SQL function correctly validates item existence, availability, server-side pricing, table-token binding, and staff authorization. Inspect the deployed RPC definition and its grants/RLS policies before enabling real payments or treating QR table orders as production-ready.

### Medium — personal activity is not connected yet

`/guest/my-activity` previously showed hard-coded sample orders and a non-functional Cancel button. This patch removes those misleading samples and removes the inert control. The page clearly explains that personal history is not connected yet. A future implementation should load the authenticated guest's own orders/bookings and only offer cancellation after a real, authorized cancellation endpoint exists.

### Medium — image quality still needs content-level curation

The supplied Haile-labeled seed file has 210 menu records but only 40 distinct image URLs, with unrelated dishes sharing photos. This change removes the misleading global salad fallback and fixes menu/cart source mismatch; it does not import that Haile dataset or claim all existing image URLs have been individually verified/matched to dishes. Photo curation should retain Tule's current menu names/prices and be checked dish by dish.

### Medium — external integration checks

The source references Supabase for menu/order/reservation/service data. Live credentials, RPC definitions, staff permissions, and reservation/service workflows were not exercised in an authenticated production session. These require a controlled test with test records before declaring end-to-end workflows verified.

### Low — setup and presentation consistency

- README points to `localhost:3001`, while the default Next.js development server uses port 3000 unless configured otherwise.
- The current palette is unchanged by this patch. A separate design pass is planned because the current dark teal/gold/amber scheme is not the desired final direction.

## Recommended manual acceptance checklist

1. Open the menu on desktop and a mobile viewport; confirm 10 items per page, next/previous buttons, horizontal swipes, page reset after searching/category changes, and no visible total dish count.
2. Add two different items, refresh, and verify both quantities remain; change quantities and confirm subtotal.
3. Proceed to checkout when Supabase IDs differ from the seed IDs; verify the chosen items still render.
4. Submit a test order to a test table and confirm it appears exactly once in the correct staff/kitchen queue with correct items and totals.
5. Test invalid, stale, or unavailable menu IDs and invalid table tokens; confirm no order is created or detached from its table.
6. Sign in using each authorized role and verify access restrictions, order status updates, room/reservation changes, and service requests.
7. Connect the activity page to authenticated guest-specific records and add cancellation only after safe authorization/validation semantics are confirmed.
