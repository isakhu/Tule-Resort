# Tule Resort app audit — 17 October 2026

## Scope and evidence

This is a source-based review of guest-facing menu/order/room flows and selected API routes, alongside Vercel build metadata available on 17 October 2026. The current production commit `36baf9b07c42fd3a15a79411e7b1b0388ebe3774` was marked **READY**; its Next.js build compiled, TypeScript completed, and 42 static pages generated.

A successful build confirms compilation and route generation, not complete business correctness. No authenticated guest/staff/admin session, live Supabase RPC transaction, or real booking was executed during this audit. The patch branch must pass its own preview build before merge.

## Fixes included in this patch

- Added a book-style restaurant menu with **10 dishes per page**, Previous/Next controls, and horizontal touch swiping. Search and category filters reset to the first page.
- Removed public-facing totals for the number of menu dishes from both the restaurant landing page and menu. The book shows page numbers only.
- Restored valid cart quantities after refresh, discarded stale/unavailable cart entries, and excluded unavailable menu rows from the menu.
- Replaced the misleading repeated-salad error image with a local neutral placeholder in menu and checkout.
- Added a no-cache `GET /api/menu` endpoint so checkout can read the same normalized menu data as the restaurant page instead of relying only on fallback seed IDs.
- Prevented both guest order endpoints from retrying a QR/table order without its table token. The QR order endpoint also resolves the kitchen department on the server instead of trusting a department ID from the browser.
- Changed regular order attribution to verify the Supabase bearer token server-side rather than trust a client-supplied `user_id`.
- Removed fabricated sample entries and an inert Cancel button from `/guest/my-activity`. It now honestly explains that personalized history is not connected yet.
- Removed the fake-success reservation fallback that generated a random reference despite not saving a reservation. The request route returns an error if the reservation RPC fails; the UI distinguishes a pending request from a confirmed booking.
- Removed an unsupported 5.0/2.4k room review claim and the unintegrated online-payment choices. The current booking UI offers pay-at-resort only until payment providers are actually integrated.
- Hardened the legacy `POST /api/reservations` route so the server calculates price from the room rate, locks payment to pending/pay-at-resort, and does not trust a submitted user ID, payment state, status or total.
- Corrected the development URL in the README to `localhost:3000`.

## Findings still requiring follow-up

### High — verify the database order and reservation functions

The app depends on Supabase RPC functions such as `create_guest_order` and `create_room_reservation`. Source code cannot prove that the deployed SQL functions validate active menu-item IDs, calculate prices from trusted database prices, enforce table-token-to-table binding, avoid duplicate orders, enforce reservation date conflicts atomically, and apply correct grants/RLS. Inspect the deployed function definitions and test with controlled records before treating ordering/booking as production-ready.

### High — legacy reservation endpoint needs atomic conflict protection

The legacy `POST /api/reservations` route checks for overlapping reservations and then inserts in a separate request. Two simultaneous requests can race unless the database enforces overlap prevention or the operation is moved into one transaction/RPC. The primary room form uses `POST /api/reservations/create`, but the legacy public route should still be consolidated or protected.

### Medium — personal activity is not connected yet

`/guest/my-activity` no longer fabricates sample orders, but it also does not display the guest's real order/booking history. Connect it to the authenticated guest's own records. Add cancellation only after a real, authorized cancellation endpoint and status rules exist.

### Medium — room booking and payment need an end-to-end test

Room requests should remain pending until the database confirms the request, and failed RPC requests must not look successful. Online Telebirr, CBE Birr and bank transfer are not connected in this UI; no online payment is being collected. Test valid and invalid dates, unavailable rooms, max guests, a database outage, duplicate submissions and overlapping date ranges.

### Medium — image quality still needs content-level curation

The uploaded Haile-labeled seed file contains 210 rows but only 40 distinct image URLs, with unrelated dishes sharing photos. It was **not** imported into Tule. Existing Tule images have not all been matched and availability-checked dish by dish. Preserve Tule's current names and prices while curating appropriate photos.

### Medium — role and integration testing remains

The staff/admin routes use bearer-token authorization patterns in several places, but authorized roles, department scoping, menu management, room/reservation changes, kitchen status updates and service requests were not tested in authenticated sessions. Verify these against the actual Supabase policies and deployed data.

### Low — design pass is intentionally deferred

The current color palette is unchanged. The user asked to revisit the colors in a later design pass. Keep that separate from the current functionality and ordering fixes.

## Recommended manual acceptance checklist

1. Open the menu on desktop and mobile: exactly 10 items per page, Previous/Next work, swiping works horizontally without disrupting vertical scroll, and no total dish count appears.
2. Search and filter by category on later pages; verify pagination resets to page one.
3. Add several dishes, refresh, adjust quantities, and compare the cart total with checkout.
4. Test Supabase-backed menu item IDs and fallback IDs; confirm checkout displays the same selected dishes as the menu.
5. Place a valid QR table order and inspect the kitchen queue; then submit an invalid/expired table token and confirm it cannot create an unbound order.
6. Try malformed, unavailable and excessive-quantity orders; confirm the server rejects them and computes totals from database prices.
7. Submit a room request, simulate a reservation RPC/database failure, and verify no fake booking number or success screen appears. Test overlapping dates and capacity limits.
8. Verify the legacy reservation endpoint cannot be used to set a client-chosen total, mark payment as paid, or assign an arbitrary user ID; add database-level atomic overlap protection.
9. Sign in using each staff/admin role and verify only the permitted departments and actions are accessible.
10. After those checks pass, connect authenticated guest activity and plan the separate visual palette redesign.
